Author surfaces that feed the mechanics

Question this demo answers: what does the author need to see between compiles for the machinery to be steerable? Issue #21 named six candidate surfaces — compile diagnostics, the proposals queue, World Model inspection, the told-ledger view, stale badges, and run reports — and asked which are essential to the POC, which collapse into one shared inspector, and which are noise. This file mocks rough screens for each candidate, then settles the collapse and the ranking below the tabs.

No live model wiring — the repo has no app yet to wire one into (the map's Out of scope already excludes "the app shell"). Every screen below is hand-populated from the Cinderella fixture (14 scenes) and, for the run report, A Christmas Carol (20 scenes) — both from fixtures/.

Six candidates collapse to four surfaces

World Model inspection and the told-ledger view are the same interaction — "show me state as of scene N" — pointed at the World Model in one tab and the Discourse Record in the other (pane B). Compile diagnostics and the proposals queue are both scoped to the card just compiled, so they share a screen too (pane A) rather than forcing the author to leave the card they're editing to find out what it just produced. Stale badges aren't a screen at all — they're two words and a popover on a list the author is already looking at (pane C). That leaves four surfaces, not six:

1 Scene compile view (diagnostics + proposals) — pane A
2 World & Discourse inspector (World Model + told-ledger) — pane B
3 Stale badges, inline on the Working Draft — pane C
4 Run report + Baked-promotion — pane D

All four ship for the POC. None was cut as pure noise — see severity → surface mapping for the one piece of information (accepted volitional commits, info-severity) that is cut from live display and pushed to the run report only, so it doesn't become the noise the author learns to ignore.

Finding: a World Model commit log is a missing piece, not an implementation detail

Pane B's scrubber ("state as of scene 12") exposed a real gap. docs/schema/story-package.md and ADR 0015 §4 only ever persist current World Model state — edition/{runId}/world-model.json is a single snapshot at the close of a run, and the live Working Draft World Model is likewise just "now." Neither lets an author scrub backward to "what did the world look like right before scene 6" — the underlying fact was never being kept.

Decision: every committed World Model change — every accepted P/E update (ADR 0005 §2) and every resolved volitional proposal (accepted or dropped) — is appended to a per-story, per-scene state-update commit log: {scene_index, entity_id, column, tier, previous_value, new_value, status}, status one of committed / proposed_applied / proposed_dropped. It's an append-only ledger, not a new authority — ADR 0005 still decides what's accepted; this just keeps what ADR 0005 decided instead of only keeping the final value. "World Model as of scene N" is the seed replayed forward through every committed/proposed_applied entry with scene_index ≤ N, which is exactly what pane B's table above does by hand. It also becomes the proposals queue's own backing store (pane A) — a proposal is just a log entry not yet resolved.

Persistence path, following ADR 0015's existing convention: story/{storyId}/draft/state-log.json for the Working Draft, edition/{runId}/state-log.json for a Compiled edition (same shape, immutable once the run completes). This is a schema addition, not a new mechanism — it changes nothing about what ADR 0005 accepts or rejects, only what gets kept afterward.

Finding: author-time closes a gap ADR 0005 deliberately left for read-time

ADR 0005 §3 ("Unattended resolution has one rule: apply, or don't") is framed explicitly around read-time — "at read time there's no author to confirm a volitional proposal." It never claims to cover author-time, where an author is present. Issue #21's own text ("Accepting one edits the World Model — so this is an authoring surface, not just a notification") is asking this ticket to fill that silence, not to relitigate ADR 0005.

Decision: at author-time, a volitional proposal is never auto-applied or auto-dropped — it sits in the proposals queue (pane A) as proposed until the author explicitly accepts or rejects it. Accept commits the log entry as proposed_applied; reject as proposed_dropped; leaving it untouched keeps it pending and does not block compiling the next scene — entry-state checks on later scenes read the World Model's last resolved value, exactly as if the proposal didn't exist yet, matching CONTEXT.md's "unattended, never blocking" preference even though an author is present here. At read-time (no author to ask), ADR 0005 §3's existing apply-or-drop invariant test is unchanged — this ticket narrows nothing there, it only names what happens in the one supervision mode ADR 0005 was silent about.

Finding: severity decides which surface, not just how loud

ADR 0005 §5 already has three severities (error / warn / info); this ticket maps them to where they render so the Scene compile view doesn't drown in log lines the author will learn to skim past:

SeverityExampleSurface
errorexit_state_contradiction, unentailed_reversion, entry_state_mismatch, unauthorized_entity_updateScene compile view (pane A), red, named against the exact contradicted field. Also logged to the run report.
warnwriter-reported beat_unsatisfied / missing_fact; a volitional proposal auto-dropped at read-timeScene compile view (pane A) at author-time; run report only at read-time (no author watching live).
infoan accepted volitional commit (ADR 0005 §5) that needed no author decision because it was already resolved by an earlier author-time acceptRun report only (pane D) — never surfaced live. This is the one category issue #21 flagged as risking "noise the author will learn to ignore," and it's cut from live display entirely rather than shown quietly.

What was deliberately left alone

  • The general UI shell, styling, and navigation around these four surfaces — build work per the map's Out of scope, not a decision this ticket makes.
  • Whether the commit log ever needs pruning/compaction at novel scale — the map's POC targets a 14–20 scene short story; an unbounded append-only log is fine at that scale and revisiting it is exactly the kind of thing that belongs in "Not yet specified" if novel scale ever forces it.
  • A UI for editing the World Model directly (outside of accepting a proposal) — plausible, but issue #21 didn't ask for it and no other ticket's decision depends on it existing for the POC.
