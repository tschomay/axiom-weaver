Prototype — throwaway — answers issue #16 only

The writer prompt contract

Question this demo answers: what is the exact input/output contract for a single scene-generation call — the output schema, the instruction layering when many constraints (plant obligations, re-anchoring, imagery ledger, voice, variance dial) land in one prompt, length control, and the failure paths (truncation, malformed output, content filters) that an unattended read-time compile cannot just retry forever.

Built against the Cinderella fixture, scene_13_the_fitting (order 13 of 14) — chosen because it is the first scene after a rollup boundary (so the cached digest hierarchy is exactly three Chapter Digests, nothing flatter or messier to show), it carries a live plant-payoff obligation (issue #8), and its re-anchoring bands span assume and reanchor at once. Prose and JSON output were written by hand against the template below, standing in for the writer call — no live model wiring, same precedent as prototype/voice-card-style-presets, prototype/context-assembler, and prototype/repetition-voice-drift-control.

The output schema

One streamGenerateContent call, generationConfig.responseFormat.text with mimeType: application/json and a responseJsonSchema using $defs/$ref — per #5's research, not responseSchema (deprecated) and not the Interactions API (its server-side store=true history would duplicate the Discourse Record the compiler already owns). propertyOrdering pins the top-level emission order to prose → scene_digest → state_updates → diagnostics: prose first so a streaming reader sees words immediately, not after the whole digest has been thought through; everything after it is written about prose that already exists.

Every field below traces to a named ADR — nothing is invented for this ticket alone. The schema is deliberately lean: it is billed as input on every call and cannot be cached (research finding #4), so a fat schema is a real per-scene tax, not a one-time cost.

Why diagnostics only has two writer-facing types. Everything else the map's Diagnostics section (CONTEXT.md) talks about — exit_state_contradiction, unauthorized_entity_update, unentailed_reversion, entry_state_mismatch, dropped-plant misses — is the compiler grading the writer's state_updates/digest after the call returns (ADR 0004 §6, ADR 0005 §5). Asking the writer to self-report those too would be asking it to grade its own homework in the same breath it does the homework — redundant with the mechanical check and a wider schema for no reliability gain. The writer only reports what only it can know: that a beat didn't fit, or that it needed a fact the context didn't supply.

Length control

Rendered as a soft target with an asymmetric tolerance band, not a hard cap: "Aim for approximately {length_budget} words. A little over is fine if the beats need room; well under is a sign a beat was skipped." Asymmetric because undershoot usually means a beat got cut (a variance-contract miss), while overshoot just costs a bit more output budget — the two failure directions aren't equally bad.

maxOutputTokens is budgeted at roughly 2× the length budget in tokens (research recommendation), which has to cover prose plus the digest/state_updates/diagnostics tail that comes after it in the same response — a budget sized to prose alone would starve the tail and manufacture truncation on every call. Tab 3 reports the actual word count the hand-written scene 13 landed at, against this budget, as the honesty check the ticket asks for ("the prose is the evidence").

Payload order, assembled for scene 13

Segment order follows ADR 0008's mandate directly: explicit-cache header (never changes within a read) → implicit-cache digest hierarchy (append-only) → uncached verbatim tail + volatile tail (mutates every scene). Where this ticket had to add its own decision: where the Voice Card's imagery ledger and the scene's own tone instruction go. ADR 0007 and ADR 0010 both describe the ledger as rendered "after the Voice Card block, before the scene's tone instruction" — but the Voice Card lives in the cached header while tone is a Scene Card field that ADR 0008 places in the volatile tail. Those two placements can't be textually adjacent across a cache boundary. Resolved here by treating "after Voice Card, before tone" as describing the volatile tail's own internal order: the ledger (which mutates every scene, so cannot live in the explicit-cache header regardless) renders inside the tail, immediately before the Scene Card's tone line. This is exactly the kind of seam the map's Notes said this ticket would have to close — three separate ADRs each solved their own piece without one of them owning where the pieces physically meet.

You are the performance engine for a Dynamic Novel Compiler. You render a fixed
Story Package into prose. You never invent plot: the scene's beats, entry/exit
state, and what the reader learns are authored — your only freedom is HOW it is
told (dialogue, imagery, interiority, micro-beat order, pacing within budget).

OUTPUT: prose, then scene_digest, then state_updates, then diagnostics, in that
order, matching the response schema exactly.

STATE UPDATES: for each World Model column you touch, propose {entity_id, column,
value}. Physical and epistemic columns (location, possessions, status, who-knows-
what) are committed automatically if they satisfy or merely extend this scene's
exit_state, and are REJECTED if they contradict exit_state, target an entity this
scene never mentions, or revert a previously-established fact without this scene
giving grounds to. Volitional columns (goal, sentiment) are proposals only —
propose freely, the engine decides whether to keep them.

MUST_STAY_HIDDEN is absolute. Prose streams to the reader before anything else in
your response is checkable — once a hidden fact is on the page, it cannot be
un-shown. Treat it as a hard constraint, not a soft preference.

Gap this exposed: the godmother isn't in this scene's characters_present, but a required beat has her walk in. ADR 0008's join is deterministic off declared fields only — it will not pull her World Model row (her bag: {nature: "fairy"}, her relationship to Cinderella) unless she's listed. She has no state to update here, so ADR 0005's footprint rule never rejects anything — but the writer still has to characterize her from nothing but her name and the beat text. Recommendation for whoever next authors or edits a Story Package: characters_present should list every character with an on-page beat, not only those whose World Model row changes. This is an authoring convention gap in the fixture (#18), not a bug in this contract — flagged here rather than silently worked around, and not fixed in the fixture file itself since that's outside this ticket's scope.
A second, sharper instance of the same class: char_prince is not present in scene 13, but the fixture's exit_state has him learning cinderella_is_the_ball_girl here. Unlike the godmother, this is a state-update, and ADR 0005 §2's footprint rule is unambiguous: unauthorized_entity_update for any proposal touching an entity absent from the scene. A correctly-instructed writer must simply not propose that row — see tab 3's state_updates, which drops it — logged as a missing_fact-style note rather than committed. The fixture's own fix is either moving char_prince into characters_present (plausible — many tellings have him present for the fitting) or moving that one character_knowledge row to scene 14, where he is present. Not this ticket's fixture to edit; flagged for whoever next touches #18.

Truncation is a required code path (research finding #5)

MAX_TOKENS under a schema returns truncated, unparseable JSON with no partial-object recovery from the API itself. Because propertyOrdering puts prose first, the common failure shape is: prose completes, and the digest/state_updates/diagnostics tail gets cut. The reader may already have streamed and read that prose — it cannot be un-shown — so the recovery has to salvage the digest, not discard the scene.

Recovered prose here is complete — the cut only reached into scene_digest.event_summary.

A second, cheap call — gemini-3.5-flash-lite, thinking_level: LOW — carrying only: the recovered prose verbatim, and the Scene Card fields a digest actually needs to reference (reader_must_learn, must_stay_hidden, pays_off, the Voice Card's imagery_palette for domain-tagging). Schema is narrowed to {scene_digest, state_updates} — diagnostics is dropped from this call; the compiler injects its own truncated_scene entry directly, since "the writer's own diagnostics" don't exist for a call the writer never finished making.

{
  "scene_digest": { "...": "same shape and, in this case, materially the same content as tab 3's — the fallback model reconstructs it correctly from prose alone, since nothing in scene_digest depends on information outside the prose it's given" },
  "state_updates": { "...": "reconstructed the same five updates as tab 3 by reading the prose's own physical claims (slipper intact and off her foot, gown restored, her location)" }
}

Run-report entry for this scene: {"type":"truncated_scene", "scene_id":"scene_13_the_fitting", "detail":"primary call hit MAX_TOKENS after prose; digest recovered via fallback call", "severity":"info"} — info, not error, because full recovery succeeded and nothing had to be guessed.

4. When prose itself is cut (the worse case)

If the closing quote for prose is never reached — the cut landed mid-sentence, well short of the length budget — recovery of a fragment is still possible, but committing a scene that visibly stops mid-clause is worse than retrying. Policy: retry the whole scene call once, with maxOutputTokens raised ~50% and a one-line addition to the scene-specific instruction ("previous attempt ran long — be more concise while still hitting every required beat"). This is the same "one bounded retry, then accept-and-log" shape ADR 0004/0005/0006 already use everywhere else on the map — this ticket doesn't invent a new policy, it applies the existing one to a new failure class. If the retry also truncates mid-prose, the fragment is committed anyway (never blocking a read-time run) with severity: error and a note for the continuity pass, which is the one mechanism positioned to patch an opening/seam on its next pass (ADR 0011) — it cannot fix a scene that stops partway through, but it can smooth what comes after it.
